## Урок 1 — теорія (з проектором, комп'ютери учнів закриті)

### 0–12 хв. Що вже є і чого не хватає 🗣

Виведи на проектор їхній код: `type Club` з дня 13 і функції з дня 14.

```typescript
type Club = {
    name: string;
    room: string;
    max: number;
    enrolled: number;
};

function describeClub(club: Club): string { ... }
function isFull(club: Club): boolean { ... }
function fillPercent(club: Club): number { ... }
```

Питання класу: **що тут не так?**

Наводки, якщо не побачать:
- дані окремо, дії окремо
- у кожній функції перший параметр той самий
- щоб зрозуміти, що можна робити з гуртком, треба перечитати весь файл
- нічого не заважає створити гурток з `enrolled: 50` при `max: 10`

> Дані й дії над ними — це одна річ. **Клас** дозволяє описати їх разом.

### 12–28 хв. Клас 🗣

Пиши на проекторі, порівнюючи з їхнім кодом.

```typescript
class Club {
    name: string;
    room: string;
    max: number;
    enrolled: number;

    constructor(name: string, room: string, max: number, enrolled: number) {
        this.name = name;
        this.room = room;
        this.max = max;
        this.enrolled = enrolled;
    }

    describe(): string {
        return `${this.name} (${this.room}), місць: ${this.max}`;
    }

    isFull(): boolean {
        return this.enrolled >= this.max;
    }

    freePlaces(): number {
        return this.max - this.enrolled;
    }
}

const club = new Club("Програмування", "215", 14, 9);
console.log(club.describe());
console.log(club.isFull());
```

Терміни, кожен через приклад:

| Термін | Що це | У коді |
|---|---|---|
| **клас** | опис типу об'єктів | `class Club { ... }` |
| **об'єкт** (екземпляр) | один конкретний | `club` |
| **властивість** | дане об'єкта | `name`, `max` |
| **метод** | дія об'єкта | `describe()`, `isFull()` |
| **конструктор** | функція створення | `constructor(...)` |
| `this` | «цей конкретний об'єкт» | `this.name` |
| `new` | створити об'єкт | `new Club(...)` |

⚠ Два порівняння, які знімають половину складності:

**Клас проти `type`.** `type` описує **форму** даних. Клас описує форму **плюс дії**. Це той самий крок, що від `type Club` до `type Club` + функції — тільно тепер вони в одному місці.

**`this` проти параметра.** Було `describeClub(club)`, стало `club.describe()`. Той самий об'єкт, тільно замість параметра — `this`. Питання класу: чи змінилась логіка? Ні. Змінилось лише, де вона живе.

Порівняння на дошці:

| Було (день 14) | Стало |
|---|---|
| `describeClub(club)` | `club.describe()` |
| `isFull(club.max, club.enrolled)` | `club.isFull()` |
| `fillPercent(club.max, club.enrolled)` | `club.fillPercent()` |

⚠ Права колонка коротша, і в ній неможливо переплутати порядок аргументів. Це і є користь, а не «так правильніше».

### 28–38 хв. Інкапсуляція 🗣

Не давай усі чотири принципи ООП списком. Дай **один**, той, що має практичний сенс сьогодні.

Постав проблему:

```typescript
const club = new Club("Програмування", "215", 14, 9);
club.enrolled = 1000;
```

Питання класу: **чому це дозволено?**

> **Інкапсуляція** — приховати дані так, щоб змінити їх можна було
> лише через методи, які перевіряють правильність.

```typescript
class Club {
    #enrolled: number;

    get enrolled(): number {
        return this.#enrolled;
    }

    enroll(): void {
        if (this.isFull()) {
            throw new Error(`Гурток "${this.name}" заповнений`);
        }
        this.#enrolled++;
    }
}
```

| | Що означає |
|---|---|
| `#enrolled` | приватна властивість. Зовні недоступна |
| `get enrolled()` | читати можна |
| `enroll()` | змінити — **тільно через метод із перевіркою** |

⚠ Тепер найважливіше зʼєднання. Скажи це прямо:

> Це та сама ідея, що в дні 25. Там ви перевіряли вільні місця **на сервері**,
> перед `INSERT`. Тут перевірка живе **всередині об'єкта**, і обійти її
> неможливо взагалі.
>
> І та сама ідея, що `CHECK` у базі з дня 6. Три рівні одного принципу:
> **не давай зіпсувати дані**.

Про решту принципів — одним рядком, щоб прозвучали: **успадкування** (клас на основі іншого), **поліморфізм** (різні класи з однаковим інтерфейсом), **абстракція** (приховати складність за простим інтерфейсом). Приклад успадкування у практиці буде, але як зіркове.

### 38–45 хв. Діаграма класів 🗣

```
   ┌───────────────────────────┐         ┌──────────────────────┐
   │          Club             │         │       Teacher        │
   ├───────────────────────────┤         ├──────────────────────┤
   │ - id: number              │         │ - id: number         │
   │ - name: string            │  0..1   │ - firstName: string  │
   │ - room: string            ├────────►│ - lastName: string   │
   │ - max: number             │         │ - subject: string    │
   │ - #enrolled: number       │         ├──────────────────────┤
   ├───────────────────────────┤         │ + fullName(): string │
   │ + describe(): string      │         └──────────────────────┘
   │ + isFull(): boolean       │
   │ + freePlaces(): number    │
   │ + enroll(): void          │
   └───────────────────────────┘
```

| Позначка | Що означає |
|---|---|
| три частини | назва / властивості / методи |
| `-` | приватне |
| `+` | публічне |
| стрілка з числом | зв'язок і множинність |

⚠ Обов'язково назви паралель, вона підсумовує весь курс:

> Порівняйте це з вашою ER-моделлю з дня 5.
>
> **Схоже:** сутності, властивості, зв'язки з множинністю.
> **Різне:** тут є **методи** — те, що об'єкт умієте робити.
>
> ER-модель описує, **як дані зберігаються**. Діаграма класів — **як програма
> з ними працює**. Це два погляди на ту саму предметну область.

## Урок 2 — практика

Учні працюють за `day-29-student.md`. Переписують `logic.ts` у класи, додають інкапсуляцію, будують діаграму класів.

### ⚠ Що НЕ переписувати в класи

Скажи це вголос на початку практики, інакше половина уроку піде на марну роботу:

| Переписувати | Не переписувати |
|---|---|
| `logic.ts` — там дані й дії над ними | `server.ts` — це маршрути, не об'єкти |
| функції, у яких перший параметр завжди `club` | `db.ts` — там одна функція, класу не потрібно |
| | `app.js` у браузері — компоненти вже є, класи їх не покращать |

Критерій, який варто дати: **клас доречний там, де є дані плюс кілька дій над цими самими даними.** Якщо дія одна — достатньо функції.

### На що дивитись

1. **Забутий `new`.** `const club = Club(...)` дасть помилку. Характерна.
2. **Забутий `this`.** Усередині методу написали `name` замість `this.name`. TypeScript підкреслить, але повідомлення незрозуміле.
3. **Клас без методів.** Просто `type`, переписаний як `class`. Це марна робота — питай, які дії він умієте.
4. **Дані з бази й класи.** `loadClubs()` віддає звичайні об'єкти, не екземпляри `Club`. Щоб методи працювали, потрібне перетворення. Це передбачено в завданні, але буде питання.

## Що піде не так

- **«Нащо, якщо працювало».** Найчастіше. Відповідь конкретна: покажи таблицю до/після з теорії. `club.isFull()` проти `isFull(club.max, club.enrolled)` — у другому можна переплутати порядок аргументів, у першому неможливо.
- **Об'єкти з бази не мають методів.** Головна технічна складність дня. Рішення в завданні: `new Club(row.name, ...)` при завантаженні. Це реальна задача, з якою стикаються всі.
- **Приватні `#` не працюють.** Вони працюють у Node 24, але якщо версія стара — буде помилка. Тоді замінити на `private` (це TypeScript-варіант, працює завжди).
- **Час.** Переписування займає більше, ніж здається. Мінімум — один клас `Club` з трьома методами. Скажи це вголос.
- **Успадкування як спокуса.** Хтось захоче зробити `class TechClub extends Club`. Дозволь у зірковому, але скажи правило: успадкування виправдане, коли між класами справді відношення «є різновидом». Інакше воно тільно ускладнює.
