## Урок 1 — теорія (з проектором, комп'ютери учнів закриті)

### 0–12 хв. Навіщо гілки 🗣

Постав задачу, у якій поточний спосіб роботи ламається:

> Ти хочеш переписати сторінку. Це три уроки роботи. Посеред другого уроку
> виявляється баг, який треба виправити **зараз**.

Питання класу: **що робити?** Твій код у половині переписаний і не працює.

Розверни варіанти:
- закоммітити недороблене → у `main` лежить непрацюючий код
- не коммітити три уроки → уся робота під загрозою, і нічого не бачить учитель
- скопіювати папку → вони вже знають, чому це погано (день 2)

```
                 ┌──── feature/my-page ────┐
                 │  коміт   коміт   коміт  │
                 ↑                         ↓
   main ─── коміт ─── коміт ─── коміт ─── злиття ─── коміт
                        ↑
                    виправлення бага
```

> **Гілка** — паралельна лінія розробки. У ній можна ламати що завгодно,
> бо `main` не змінюється.

| | |
|---|---|
| `main` | головна гілка. Тут завжди робочий код |
| гілка функції | тут робиться одна конкретна зміна |
| **злиття** (merge) | перенести зміни з гілки в `main` |

### 12–25 хв. Команди 🗣

Напиши на дошці — вона висітиме весь урок:

```
git switch -c feature/my-thing    створити гілку й перейти в неї
git switch main                   перейти в main
git branch                        список гілок; зірочка — де ти зараз
git merge feature/my-thing        влити гілку в поточну
git branch -d feature/my-thing    видалити гілку після злиття
```

⚠ Дві речі, які варто підкреслити:

**1. Файли фізично змінюються при перемиканні.** Це дивує. Покажи на проекторі: перейди в іншу гілку, і вміст файлу у VS Code зміниться сам.

**2. Не можна перемикатись із незакомміченими змінами.** Git не дасть. Правило: спочатку коміт, потім `switch`.

Про назви гілок — домовленість, яка є в кожній команді:

```
feature/enroll-form    нова функція
fix/empty-search       виправлення
docs/requirements      документація
```

### 25–38 хв. Конфлікт злиття 🗣

Найважливіша частина дня. Учні бояться конфліктів, а вони прості — треба один раз побачити.

> **Конфлікт** виникає, коли **один і той самий рядок** змінили по-різному
> у двох гілках.

⚠ Скажи одразу те, що знімає страх: **конфлікт — це не поломка**. Git просто не знає, який варіант правильний, і питає тебе.

Покажи на проекторі, як він виглядає у файлі:

```
<<<<<<< HEAD
    <h1>Гуртки нашої школи</h1>
=======
    <h1>Шкільні гуртки та секції</h1>
>>>>>>> feature/new-title
```

| Частина | Що означає |
|---|---|
| між `<<<<<<<` і `=======` | версія з **поточної** гілки |
| між `=======` і `>>>>>>>` | версія з гілки, яку зливаєш |

Що робити: **видалити маркери й залишити те, що правильно**. Можна взяти один варіант, можна обидва, можна написати третій.

⚠ Головна помилка: забути видалити самі маркери `<<<<<<<`, `=======`, `>>>>>>>`. Тоді вони залишаться у файлі й зламають код. У VS Code вони підсвічуються.

Після виправлення:

```
git add .
git commit -m "розвʼязано конфлікт"
```

### 38–45 хв. Читання діфів 🗣

Остання навичка Git, і вона потрібна щодня.

```
git diff              що змінено, але ще не в коміті
git show              що змінив останній коміт
git log -p -- файл    історія змін одного файлу
```

Покажи на проекторі вивід `git show`: рядки з `+` додані, з `−` видалені.

Питання класу: **нащо це, якщо є VS Code?**

Відповідь: щоб зрозуміти, що змінилось, не читаючи весь файл. При 200 рядках коду й правці в трьох місцях діф показує рівно ці три місця.

І про **Pull Request** — одним абзацом, як поняття:

> У командах гілку не зливають самі. Автор відкриває PR — «прошу перевірити
> й влити». Інші читають діф і залишають коментарі. У більшості компаній
> влити без схвалення технічно неможливо.
>
> Це те саме, що ви робите зараз, тільно з обов'язковим кроком перевірки
> перед злиттям.

Демонструвати не потрібно — учні не мають акаунтів. Достатньо, щоб вони знали слово й розуміли ідею.

## Урок 2 — практика

Учні працюють за `day-28-student.md`. Роблять: гілку з реальною зміною, навмисний конфлікт, читання діфів, злиття.

### Хронометраж

| Частина | Хвилин |
|---|---|
| Гілка й реальна зміна | 15 |
| Навмисний конфлікт | 12 |
| Читання діфів | 8 |
| Друга гілка й злиття | 8 |
| Здача | 2 |

### На що дивитись

1. **Перемикання з незакомміченими змінами.** Git відмовить із незрозумілим текстом. Правило: коміт, потім `switch`.
2. **`git push` з гілки.** Перший раз потрібно `git push -u origin ім'я-гілки`. Без `-u` буде помилка з підказкою. Це в завданні є.
3. **Забуті маркери конфлікту.** Перевіряй очима після злиття — код із `<<<<<<<` не працює.
4. **Конфлікт не виникає.** Учень змінив різні рядки, і Git злив автоматично. У завданні описано, як створити конфлікт **навмисно** — на тому самому рядку.
5. **Гілка не видаляється.** `git branch -d` відмовить, якщо гілка не злита. Це захист, а не помилка.

## Що піде не так

- **Конфлікт не виникає.** Розібрано вище.
- **Страх зламати проект.** Скажи заздалегідь: усе, що закоммічено й запушено, повернути можна. Гілки — найбезпечніша частина Git.
- **Гілок стає багато й учень губиться.** `git branch` показує, де він. Правило: одна гілка — одна зміна, і зливати одразу після завершення.
- **Час.** Зіркові завдання, скоріш за все, не встигнуться — це нормально.
